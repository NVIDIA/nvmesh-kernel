Note: For proper editing in slickedit, I associated the extention ".txt" with "C/C++" (tools/options/languages/file_extention_manager)

Indentation:
-----------
	4, using tabs
	Multi-line expressions should use parentises, and let slickedit do the job, such as:
	if (a &&
		(b ||
		 c)) {

Alignments:
----------
- always put at least one \t before the variable name
	int					a;
	unsigned long		b;

Comments:
--------
	\t// Always put at least one tab before the "//", and one space after it.

Multi-line Comment
------------------
Two styles
	/*
	 * Text starts here
	 */
or
	//
	//

Comment-out code
----------------
- Preferable
#if (0)
#endif	// if (0)
- Also OK: Slickedit "// "

Conditional Macros
------------------
- The #else and #endif should mention their #if
#if (xxxxxxxxx)
#else	// #if (xxxxxxxxx)
#endif	// #if (xxxxxxxxx)

Shortcuts:
---------
- seg:		disk_segment
- n_:		number_of_
- mgmt:		management

spaces:
------
- As in english, some examples
- if (...) {
- a, b;

empty_lines:
-----------
- Usually, no more than one line
- One Empty lines between functions
- One empty line between the variables declarations and the "FIN" (or first line of code)
- No need for an empty line after the FIN, and around the FOUT

if:
--
- Always use {}, It survives merge better, and makes things more uniform
	if () {
		xxx();
	}
	else if {
	}
	else {
	}

Multi-line condition/calculation:
---------------
	No consensus here :-)
	Ronen's style is:
	if (	x &&
			y) {
		aaaa();
	}

Assignments inside an "if":
-------------------------
Better avoid,  E.g., prefer
	x = xxxx();
	if (x) {
over
	if (x = xxxx())
We are good with
	if (xxxx()) {
Are we good with
	if (xxxx() < 0) {

switch:
------
	switch (xxx) {
	case a:				return xxx;
	case bbbbbbbbb:		return zzz;
	default:
		yyy();
		break;
	}

Types:
-----
	int				(32 bits)   	%d, %u, %x
	long long		(64 bits)   	%ll, %llu, %llx
	How about u32, u32_t, ...

	What about ufast - variable with CPU register width for performance reason.

BOOL (C99 _Bool / stdbool.h):

Starts with a quesion word, preferably "is", such as:
	BOOL	is_valid;
- Value: true/false

Typedef:
-------
- Do we want to use typedef, vs. (struct xxxx)

goto:
----
Used mostly for "goto out", and alike.
- Avoids the indentation of "else"
- No need to consider the effects in the code that follows the else

Logging:
-------
- _Ef(): An error that should never happen
- _Wf(): A warning. Note that it goes to Syslog, so should not be used for expected and well handled use cases
- _IMf(): Info Major, goes to Syslog!
- _Tf(): A standard debug msg
- Use a single space (rather than ", ") as a separator.
- Always use a "=" with no spaces between the name and the value such as
  "fd=%d hostname=%s"
- "seg=%.8s", nvmeibt_disk_segment_id_str(disk_segment)
- "%s" for the other config objects
- "cid=0x%x-", cid

Cross files references:
----------------------
- The name starts with nvmeibt_<obj_name>_
- Locals: static ...

Variables declarations & initialization:
---------------------------------------
Usually, avoid initialization as part of the declaration
- It is code that runs before the "FIN"

Brackets:
--------
Use them generously, specifically
- (is_a ? xxxx() : yyyy)
- Every use of a macro variable

Naming (of functions, variables, ...):
-------------------------------------
- Take the effort to give booleans a positive names. It is easier to understand if (!is_good_to_go) than if (!is_not_good_to_go)
- Names should be meaningful, and practically "document" its role. This often requires
  the use of long names. Still, make an effort to shorten them.
- Please rename/refacor things if the name does not match the role
- [Ronen] Whenever I try to understand a piece of code (usually since something doesn't work well),
  I go into a renaming process until I figure it out. Please save me the effort.
- Names that are used in mathematical calculations should always include units, and be fully explicit.
  In the past we had several tough data-corruption bugs that could have been avoided,
  and easily detected had we followed this rule.
  E.g., "total_bytes = n_4K_pages * n_bytes_in_4K_page"
- When do we use save/store/write read/restore
  memory / disk / data_for_restore(dirty-bits)

Line length:
-----------
- Feel free to exceed the 80 characters limit. Still, try to make it fit a typical screen (~160 characters ?). 200 chars should be rarely exceeded.

Scope rules:
-----------
- Over time we replace direct access to the internals of other objects with a functional get()

Macros usage:
------------
- Benefits: Logging of the caller's line in the code

FIN/FOUT:
--------
- Should be added to most functions.
- Short functions that anyhow write a meaningful log msg, often avoid the FIN/FOUT

start, end, length:
------------------
- Prefer the representation of <start, length> over <start, end> it does better in avoiding the "+1" noise.

nvmeibt_common.h:
----------------
- Try to use its APIs
- *ALLOC*
- UUID
- CSV parsing

nvmeibt_bm (Buffer manager):
---------------------------
- Do we want to use it outside the logging. Why?

Comparisons:
-----------
- We are good with if (n_x) // over if (n_x > 0)
- We prefer if (n_x == 0)	// over if (!n_x)

Return value:
------------
Always rv
- 0: OK
- <0: Err
- >0: ?
- void when the rv is unused
Try to use the name "rv" for the return value (Its role is clear even in a  1 line diff)
Try to initialize "rv = <scalar>" at the declaration line (it is easier if no need to search backwards)

Functions:
---------
- When no arguments, always put void, such as func_name(void). Otherwise, the compiler might ignore the args in the call

Constants:
---------
#define BIT_4 (0x1 << 4)

Order of struct members:
-----------------------
By Alignment (including array of) - Long-long/pointer, int, short, char
