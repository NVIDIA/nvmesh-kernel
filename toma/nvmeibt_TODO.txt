Thoughts:
  - At client_load, the client generates a UUID
??  - A client registers with every TOMA separately. Per (?disk/PRAID/segment/server?) with its UUID, and receives an id_for_locks
    - Ronen: I suggest per-segment, so that we can assign a new id both on every registration (upon volume and phys disk changes).
      - Since disks might be reconnected with a new id_for_locks, while other disk continue to work normally, the id cannot be per server.
      - Changes to the topology do not require a new id
      - Disconnecting from a disk voids all of the IDs that were used on this disk
      - There is a "natural" relationship between the domain of locks (per segment), and an id_for_locks.
      - Future proof, what if we change things like assigning QP per segment (and not per disk) on separate NICs.
  - New id_for_locks are generated using a (64 bits) counter that increments per assignment (no reuse of id on a running TOMA).
  - The client uses the same UUID with all the TOMAs
  - Curently, the UUID has no concrete use. It was proposed in order to identify the client cross servers.
Use-cases
- Client disconnects voluntarily, or accidentaly (network), or by TOMA (brute force) (per ???)
  - TOMA marks the client's id_for_locks as void_and_in_recovery.
  - TOMA runs locks recovery for this id_for_locks
  - When done with the recovery, this id_for_locks is forgotten
  - The client cannot work with this TOMA (server/disk/segment) unless it re-registers
- Client is paused on disk
  - Probably due to a QP with the disk that died
  - All of the client's locks on this disk are lost (might be cleared and recovered by TOMA).
- Client is paused by TOMA on a RAID(1/5 (RAID0 too? Volume too?)).
  - Probably due to a change in the topology. Not breaking any QPs
    - A client returns a pause_ack when it is done with all the current actions.
  - The client has to re-register in order to validate that it works with the current topology
    - The client will probably have to get a new topology
  - Question: Do we keep the old id_for_locks?
    - Answer: We can. Is it worth it?
      - Not needed, since there are no active transactions
      - TOMA side - it requires distinguishing between registrations, instead of always providing a new id_for_locks.
        id per disk is almost just as easy.
- Client re-registration
  - On cont (after pause on disk), the client has to re-register, and re-lock on all the paused disks, using its new id_for_locks.
    - This is true also for locks that were already aquired successfully.
      - Since we assume that the old id_for_locks is in recovery, the client cannot trust
        any of its previously held locks (they might be cleared by TOMA, and even taken by a different client).
    - Fully completed reads/writes, do not need to be repeated (re-locked ...).
      - Also, no need (and cannot, release locks that their data was fully completed)
    - Optimization: The client can overide its prev id_for_locks (cmpxchg with NONE/OLD_id_for_locks)
      Otherwise, it has complain to TOMA (on segment + lock_idx), if the old lock is still there (not yet recovered)
- Multiple recoveries
  - When a client disconnects & TOMA is running a recovery on a segment
  - The client can have multiple IDs - the current one, and several that are in recovery
  - With the current design, I cannot think of a scenario where some segments continue
    to work with a valid old ID, and some have to switch to a new one. but using an ID per
    segment will put us on the safe side.
